**Status**: Decided

## Context

`STD-001` requires a hexagonal backend; `VER-004` requires every door's writes to enter through the same application use cases; `API-001` and `MCP-001` both require their door to expose the same operations as the UI, never a parallel implementation.

## Decision

`backend/domain/` and `backend/usecases/` import no web framework, no database driver and no adapter module (checked by import-direction analysis, `tests/test_walking_skeleton.py`, `INT-PLANS-028`). `backend/usecases/service.py`'s `PlanService` is the one write path: `backend/adapters/http/routes.py` (REST), `backend/adapters/mcp/server.py` (the nine MCP tools) and the importer all call its methods directly, with no adapter re-implementing validation, id allocation, or versioning logic of its own. `backend/usecases/ports.py` declares the `PlanStore` protocol the service depends on; `backend/adapters/store/postgres.py` is its only implementation.

A REF-Plan dataset moves through this path as a plain `dict`, validated structurally (`backend/domain/models.py::validate_dataset`) rather than mapped onto a whitelisting dataclass - the mechanism that makes `INT-PLANS-002` ("no field the engine invented, and none it silently drops") true by construction rather than by discipline.

## Rationale

- One write path is what makes "a write through any door is visible through every other door" (`API-001`, `MCP-001`) a structural fact instead of a promise kept by convention.
- Import-direction testing (rather than a design review) keeps the hexagonal boundary enforced on every change, the same discipline `STD-002` applies to the frontend's MVVM boundary.

## Alternatives considered and rejected

- **A thin REST-only core with MCP tools wrapping HTTP calls**: rejected by `REF-MCP.md` section 2 and anti-pattern 2 - a tool wrapping an endpoint of the same app is a second hop with its own failure modes, not a door into the use case.
- **Typed dataclasses for the dataset**: rejected because a dataclass with a fixed field set silently drops any field it does not know about, which is the exact failure `INT-PLANS-002` exists to catch; structural validation over plain dicts preserves fields the engine has no opinion about.
