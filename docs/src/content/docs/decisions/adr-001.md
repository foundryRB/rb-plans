**Date**: 2026-09-13
**Status**: Decided (amended 2026-09-20: the canonical source moved to `bootstrap-plan`, and this repo vendors it; amended 2026-09-21: the page frame travels with the renderer, and the identity's faces and stage travel in that frame)

## Context

`PLN-002` makes the engine's plan view the renderer `bootstrap-plan` ships, not a reimplementation; `PLN-003` forbids two hand-maintained copies of it. The engine has two consumers of a plan render: the cockpit's `Plan · Render` screen (a live view over a fetched dataset) and the Export Composer (the standalone, self-contained HTML file, `EXP-001`). `EXP-001` also requires the export and the cockpit's display of the same plan to be byte-identical, which is a stronger claim than "the same look."

## Decision

There is exactly one canonical renderer, and it is **`bootstrap-plan`'s** (`galaxies/press/skills/bootstrap-plan/renderer/`), framework-free, `textContent`/`createElement` only (`REF-Plan.md` section 6). The skill that scaffolds a plan and the engine that serves one render it with the same file, because a plan is a Press artifact first and this engine is one of its consumers, not its owner.

This repository holds that source as a **pinned, byte-identical vendored copy** at `renderer/`, recorded in `renderer/PINNED.json` by its only writer, `renderer/update-vendored-renderer.sh`. A copy rather than a fetch because the playbook is a separate private repository: a build that reached for it would need a cross-repo secret in CI and would break whenever the playbook moved, and keeping this build hermetic is worth more than freshness that nobody asked for. Freshness is an operator's act instead: `renderer/check_pin_drift.py` asks whether upstream has moved, on the caller's own credential, never in a pipeline. `tests/test_vendor_pin.py` re-hashes the copy offline on every push and asserts no workflow reaches the playbook.

A renderer fix therefore lands in the playbook first and arrives here as a pin bump. A fix made directly in `renderer/` is a fork, and the pin test fails it.

Both consumers reach the vendored copy without forking it:

- **The Export Composer** (`backend/adapters/export/composer.py`) reads `renderer/plan-renderer.js`, `renderer/plan-renderer.css` and `renderer/plan-page.html` directly, at a path computed from the repo's own layout (`backend/` and `renderer/` as siblings, true both in a source checkout and in the released image). It fills the page frame with the dataset, the renderer script and the CSS, exactly as the skill does, so an export and a scaffolded plan are the same page. This is the strongest possible form of "no fork": there is only one file, read, never copied.
- **The cockpit** loads the identical bytes as static assets (`frontend/public/renderer/`), produced at build time by `renderer/project-to-frontend.mjs` (run via `predev`/`prebuild`/`pretest` npm hooks, one directory below its own source so it needs no path back into `frontend/`) - a mechanical, byte-for-byte projection, verified by `tests/test_renderer_bundle.py`. The assets' names carry the SHA-256 values recorded in `renderer/PINNED.json`; `PlanRenderMount` reads that manifest to request the matching paths. A new renderer therefore gets a new URL when the edge caches static assets. The SPA serves HTML with `Cache-Control: no-store`, so a page load requests the current asset paths. `PlanRenderMount` calls `PlanRenderer.render(dataset, container)` directly against the dataset the cockpit fetched over the REST door - the same function, not a second implementation (`INT-PLANS-003`).

**The identity travels inside the vendored files.** Its faces arrive inlined in the page frame's `/* PRESS palette */` block, from the design hub's `generated/faces.css`, so nothing embeds a face at export time and an identity without faces of its own carries none. Its stage arrives in the same frame, from the hub's `generated/stage.{html,css}`, fixed behind the opaque plan. The cockpit loads only the script and the stylesheet, so the application keeps its own faces, ground and stage, and the sheet it loads stays light.

**`PLN-003` now holds across the scaffold too.** It did not until 2026-09-20: `bootstrap.py` carried its own renderer, about fifty functions drawing the same eleven REF-Plan sections over the same dataset shape as `plan-renderer.js` and sharing three function names with it. Two implementations of one spec, each fixed on its own (playbook#283, playbook#330). The scaffold now composes the canonical source, and this repo vendors it, so all three renders come from one file.

The identity travels with it the same way every other Press artifact gets one: the sheet's brand values live in the maintained `/* PRESS palette */` block that `sync_press_palette.py` stamps from the design hub, scoped to `.pr-root`. Lane hues and the status trio stay instrument-owned, because they carry meaning rather than brand.

## Rationale

- A single file read directly by the Export Composer cannot drift from itself.
- A build-time projection script (rather than a runtime fetch or a manual copy-paste) makes the cockpit's copy mechanically reproducible and testable (`INT-PLANS-004`).
- One page frame for every standalone plan file means the page around the plan cannot drift between the skill and this engine, the way a second page kept in Python once did.

## Alternatives considered and rejected

- **The cockpit re-implements the plan view in React**: rejected outright by `PLN-002`; it is exactly the fork this ADR exists to prevent.
- **The Export Composer executes the renderer server-side (a headless browser or a JS runtime in Python)** to produce pre-rendered HTML: rejected as unnecessary complexity - `REF-Plan.md` section 6 already specifies a framework-free, render-on-load script, so the Export Composer only needs to *embed* it, and the browser does the rendering identically in both contexts.
- **A shared npm package extracted now** so `bootstrap-plan` and this engine both depend on it: rejected. It would put a registry, a release cadence and a version range between a renderer fix and the plan it fixes, to share one script and one sheet between two consumers that a pinned copy already shares. The scaffold also has no JavaScript toolchain and wants none: it is a Python script that emits a file.
- **This repo keeps ownership and projects into the playbook**: rejected, and it is worth saying why, because it was the original shape. It has the dependency backwards. A plan is a Press artifact, defined by `REF-Plan.md` and scaffolded by a playbook skill; this engine is one consumer of that definition. Ownership here would mean anyone using the playbook alone could not make a plan that looks like a plan.
- **Fetching the canonical source at build time** instead of vendoring it: rejected, because it makes this build depend on a private repository and a cross-repo secret. That is the coupling the pin exists to remove, and the same conclusion `foundry-console` reached for the delivery helpers it vendors.
