## Context

`BND-003` forbids the app building its own auth; the signed proposal puts access control at the platform edge. On this Foundry, an app is reachable at its hostname with no gate at all unless a realm is granted AND the app's own chart renders the proxy that enforces it (`REF-Foundry.md` sections 3/5). `MCP-001`'s agent door cannot complete an interactive browser login, so the human-surface proxy cannot front `/mcp` without breaking `DONE-002`.

## Decision

Two credential schemes, one per audience (`REF-Foundry.md` section 3, `REF-MCP.md` section 7):

- **The human surfaces** (the cockpit, the REST API) sit behind an oauth2-proxy sidecar (`k8s/templates/deployment.yaml`, guarded by `.Values.auth.oidc.enabled`) once `foundry-onboard-keycloak`'s realm grant lands. `--provider=oidc` (not `keycloak-oidc`, whose audience check on the default `aud` breaks every callback); `--api-route=^/api/` (singular flag; the pluralized one crashes the proxy) makes an unauthenticated REST call answer `401` rather than redirect to a login page.
- **The machine door** (`/mcp`) is skipped by the proxy (`--skip-auth-route=^/mcp`, header stripping disabled) and gated instead by the app's own fail-closed HTTP Basic key (`backend/adapters/http/auth.py`, `MCP_USER`/`MCP_PASSWORD`, `auth.existingSecret: vf-plans-mcp`). `/mcp` answers `503` while the key is unset, `401` on a wrong or missing credential - never open, and never gated by a token that also gates the human surfaces.

`PLANS_AUTH_SCOPE` narrows the app's own Basic gate to `/mcp` alone, and is rendered only under the same `auth.oidc.enabled` guard as the sidecar: setting it unconditionally would leave every route open with no gate at all whenever the realm is not yet granted, so the narrowed-gate state stays reachable only together with the proxy that makes it safe. The engine itself authenticates no user of its own: no login route, no session store, no user directory (`BND-003`, `INT-PLANS-035`) - the `who` on a decision or log row is authored text, not a session identity (DSN-008).

## Rationale

- One credential per audience means a leaked human session cookie cannot reach the machine door and a leaked machine key cannot reach the human surfaces.
- Gating `PLANS_AUTH_SCOPE` on the same condition as the sidecar keeps the "narrowed gate" state impossible to reach without the proxy that makes it safe actually being present.

## Alternatives considered and rejected

- **A bearer token issued by the proxy's own OIDC client for the machine door**: rejected - it hands one credential to two audiences, the opposite of the platform's rule, and would require reconfiguring a realm client this delivery has no grant to touch.
- **No gate on `/mcp` at all, relying on network policy**: rejected - `BND-003`'s write path (nine MCP tools, all mutating) would be open to anyone who can reach the hostname.

## Amended (2026-09-14): the chart mints the machine door's key

The `vf-plans-mcp` Secret is minted in this namespace by the chart itself (`k8s/templates/mcp-key.yaml`) instead of being applied out of band: a generate-if-absent `Sync` hook at wave -1, with its `ServiceAccount`, `Role` (create secrets; get and patch only `vf-plans-mcp`) and `RoleBinding` at wave -2, ahead of the Deployment, which reads `MCP_USER` and `MCP_PASSWORD` by required reference. The chart names the Secret itself, so `auth.existingSecret` and `k8s/secrets/vf-plans-mcp.env.example` are retired, and the pod never starts without its key.

The key needs no seeding because nobody needs it before it exists: the cockpit's Connect agent panel reads it back through `/api/agent-credential` (`INT-PLANS-045`), which makes it the platform's Class 3a, generated in-cluster (platform ADR-034, amended 2026-09-14). The guard leaves the key already live in the namespace untouched, so connected agents keep working. Rotating it is deleting the Secret, syncing the app so the Job mints a fresh key, restarting the Deployment, and reconnecting each agent with the command the panel then shows.
