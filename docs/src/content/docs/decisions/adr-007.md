**Date**: 2026-09-13
**Status**: Decided

## Context

The released image set is a promotion-record fact (`REF-Foundry.md` section 7's reconcile check, `INT-FOUNDRY-061`): the deploy branch's image-updater aliases are bound to exactly the images this repo's compose file (plus the docs image) declares. A third image either fails this repo's own release or, worse, gets no alias and pins its first tag forever with no crash and no red status.

## Decision

`devops/docker-compose.yml` declares exactly one `build:` service, `app`; `devops/Dockerfile` is a three-stage build (`frontend-build` on `node:22-alpine`, then a Python stage that assembles `backend/`, `renderer/`, and `tests/deployed/` with its runtime dependencies, copying the built frontend's `dist/` into `app/static/`). `docs/Dockerfile` (unchanged, not part of this decision) publishes the second and only other released image. FastAPI serves the REST API, the MCP door, and the built cockpit bundle as static files, all from `vf-plans-app`.

## Rationale

- One image means one alias (`vf-plans-app`) for the image updater to track, matching the promotion record's expectation exactly.
- The natural instinct on a two-tree repo (`backend/`, `frontend/`) is two images; resisting it here is deliberate, not an oversight left for a later split.
- Carrying `tests/deployed/`'s runtime dependencies (`pytest`, `csd-pytest-intent`, `httpx`) in the production image is a recorded, deliberate widening of its surface: the in-cluster verification Job (`INT-PLANS-042`) runs from this exact image, and packaging a second "test" image just for that one Job would itself be the third-image failure this ADR exists to avoid.

## Alternatives considered and rejected

- **Separate `vf-plans-backend` and `vf-plans-frontend` images, with the frontend served by nginx**: rejected by this ADR - it doubles the release surface for no operational gain, since the frontend has no independent scaling or deployment need.
- **A dedicated test-runner image for the verification Job**: rejected as the third-image failure this ADR is written to prevent; the app image already carries everything the Job needs.
