**Date**: 2026-09-13
**Status**: Decided

## Context

`STD-002` requires the frontend to be MVVM, checked the same way the backend's hexagonal boundary is (`STD-001`): by import direction, not by folder naming convention alone.

## Decision

`frontend/src/api/client.ts` is the only module in the cockpit that calls `fetch()`; it mirrors the REST door's endpoints 1:1 with no client-side business logic. Every screen's state and every write is owned by a `use*ViewModel` hook (`frontend/src/viewmodels/`) that calls `client.ts` and exposes plain data and callbacks. View components (`frontend/src/views/`) render that data and forward user events to the view model's callbacks; they hold no `fetch` call and no import of `api/client` (enforced by `frontend/src/__tests__/mvvm-boundary.test.ts`, a static import-direction scan, `INT-PLANS-029`).

`PlanRenderMount` (`frontend/src/components/`) is the one exception worth naming explicitly: it loads the canonical renderer script as a browser asset and calls its `render()` function, which is presentation (ADR-001), not a second data-access path - the dataset it renders is already fetched and passed in as a prop by `PlanRender`'s view model.

## Rationale

- A static import check catches a boundary violation at the moment it is introduced, the same value the backend's equivalent test provides.
- Keeping the API client REST-shaped (one function per endpoint) rather than domain-shaped (one function per plan operation) keeps it a thin mirror of the door, not a second application layer with its own opinions.

## Alternatives considered and rejected

- **A global state store (Redux/Zustand) with connected components**: rejected as unneeded complexity for five screens whose data is either a single plan or a plan list; React Router's URL params plus per-screen view models already give each screen exactly the state it needs.
- **Fetching directly in views with `useEffect`**: rejected outright by `STD-002`; it is the violation this ADR and its test exist to prevent.
